# 价格持久化规模实验：2026-09-24

[English](README.md)

本目录保存了 **100 万与 1000 万条 `latest` 冷热合成事件**的首次费用迁移、30 天重算，以及仅在 100 万规模执行的旧版／新版真实 HTTP 长范围查询对照。**100 万条 `five-dim`** 首次正式运行因接收缓冲丢弃而失败，缩小旧回放页批次后的同数据复测已完整通过；两次原始报告均保留。数据见 [latest 1m](latest-1000000.json)、[latest 10m](latest-10000000.json)、[five-dim 失败](five-dim-1000000-before-fix.json)与[修复复测](five-dim-1000000.json)、[1m 的 119 天 HTTP 对照](query-comparison-1000000.json)及[运行环境](environment.json)。

## 实验输入与复现

实验机 `geelinx-my` 为 Linux/amd64、6 个逻辑 CPU、约 9.49 GiB 主机内存。开始生成时磁盘可用量分别为 latest 1m **24.98 GiB**、latest 10m **31.92 GiB**。所有正式任务均以 cgroup 限内存 7 GiB、swap 512 MiB，`GOMEMLIMIT=5GiB`，未限制 CPU 配额；时区固定 UTC。Go 为 1.26.2，SQLite 驱动为 `go-sqlite3 v1.14.48`，基准二进制带 `sqlite_trace` 构建标签。产品代码基线为 `4e41adc293f10469e4523a300432ace8b90dfc05`；修复版另有两处旧迁移页批次调整，二进制哈希单独记录于环境文件。报告中的主机内存不是 cgroup 限额。

两次均固定锚点 `2026-09-23T00:00:00Z`、种子 `20260923`、生成器版本 `production-v10-pricing-storage`、500 个身份、50 个 API Key、50 个模型、**50 条实际价格规则**和 1% 失败率。数据跨 120 天：1m 为热 75 万／冷 25 万、最近 30 天 25 万；10m 为热 750 万／冷 250 万、最近 30 天 250 万，热／冷各覆盖 90／30 天。独立构造器先用现有容量生成器生成和聚合合成数据，再在专用文件上物理移除新增费用列、价格控制表及对应迁移版本，核对旧列、冷热行数、Token、汇总请求数与游标，才开始计时首次升级。准备时间含生成与旧 schema 转换，**不计入**费用迁移 M1–M6。该 `latest` 输入已应用早期五维／索引迁移，所以其升级时间不能充当待执行旧五维迁移或建索引的测量。

从仓库根目录复现，可在具备上述资源限制的 Linux 隔离任务内分别把下列命令的规模参数设为 `1000000` 或 `10000000`，**顺序运行**。每次使用全新输出目录；脚本只运行指定的一组规模／场景，保留合成库、M1 备份、报告及环境清单，不自动清理。正式运行应预留数据、WAL、备份与生成阶段所需磁盘空间。

```bash
export TZ=UTC GOMEMLIMIT=5GiB
export PRICING_BENCHMARK_REVISION=4e41adc293f10469e4523a300432ace8b90dfc05
internal/benchmark/scripts/run-pricing-benchmark.sh <新输出目录> 1000000 latest 2026-09-23T00:00:00Z
```

首次升级走真实 M1 备份及 M1–M6 迁移函数；重算走真实价格服务和仓储，期间持续写真实 SQLite inbox，并通过实际统计路由查询。两次正式 `latest` 实验均直接运行已构建的基准二进制；上述脚本提供同参数的可重复入口。`PRICING_BENCHMARK_REVISION` 只写入环境清单，不固定源码；CMT34 工具以单独的源文件哈希和二进制哈希溯源，不应把当前工作树未冻结的其他内容当作该次运行的一部分。

## 100 万条结果

迁移期间每 20 ms 独立提供一条合成消息，经容量 4096 的测试缓冲区由单 worker 调用真实 inbox 写入口；重算期间同样持续提供。迁移阶段提供／提交 **20,046／20,046**，重算阶段 **7,476／7,476**，两阶段丢弃、写入错误均为 0，峰值缓冲分别为 13、10。迁移阶段“调用写入口→事务提交”的 p95/p99/最大延迟为 **53.50/86.84/265.94 ms**，“提供→提交”p95 为 **65.48 ms**；重算阶段相应为 **7.94/164.96/218.48 ms** 与 **138.05 ms**。这验证了该约 50 条/s 负载的持久接收及积压情况，不代表 CPA 网络投递端到端延迟，也不是最大可持续接收速率。原始 inbox 行数与哈希在磁盘上逐行核对；业务事件在升级／重算后追赶。

| 资源或写入观测 | 首次升级 | 30 天重算 |
| --- | ---: | ---: |
| 进程 RSS 峰值 | 605.9 MiB | 639.7 MiB |
| WAL 采样峰值 | 35.58 MiB | 66.48 MiB |
| 主库＋WAL／SHM＋M1 备份采样峰值 | 1.678 GiB | 1.708 GiB |
| 单 writer 连接连续 `InUse` 最长采样段 | 1,799.9 ms | 950.0 ms |
| writer 连接池排队次数／累计等待 | 2,103／111.39 s | 357／49.57 s |
| SQLite trace 事务数；最长写入上界／下界 | 22,053；205.87／204.81 ms | 7,825；214.20／213.62 ms |

资源按 **50 ms** 采样，峰值可能遗漏更短尖峰；磁盘合计包含 M1 备份。升级任务 cgroup `memory.peak` 为约 **2.79 GiB**，包括未计入上表阶段 RSS 的准备过程与计费页缓存。`InUse` 是连接占用，连接池累计等待可由并发请求叠加，二者都不是 SQLite 写锁时间。`sqlite_trace` 的**上界**从事务首条写语句开始计至 COMMIT／ROLLBACK 完成，可能包含首写等待；**下界**从首条成功写语句完成计至提交语句开始，不含提交尾部。表中两个“最长”是各自集合的极值，未必属于同一事务，不能读成精确锁区间。自动提交写另计，未混入事务数或时长。未运行主动抢锁探针。

重算期间真实统计路由返回 `costs_busy` **1,485** 次、其他错误 0 次，费用读取由产品门禁暂缓。runner 内部覆盖 120 天合成数据的单次 Overview、Analysis 查询在升级后／重算前分别为 100.38、938.44 ms；重算并处理 inbox 后分别为 67.53、950.19 ms。这些单次值**不是旧版性能基线**。

## 1000 万条结果

M1–M4 含真实备份及事件费用回填，M5–M6 完成汇总费用和完整校验；最终 Overview 游标为 10,000,000，费用 NULL 行为 0。30 天实际目标与已处理均为 2,500,000，重算用时 1,301.036 秒。随后 243,703 条保留消息各生成一条事件，追赶吞吐约 **6,879 事件/s**。整次 runner 从开始到结束约 **7,393.766 秒**，其中准备 2,460.704 秒不计入迁移。

两阶段仍按每 20 ms 独立提供消息，使用同一容量 4096 的测试缓冲和真实 inbox 写入口。迁移期提供／提交／落盘核对均为 **178,651**，重算期均为 **65,052**；丢弃与写错误各为 0，峰值缓冲为 11／18。迁移期“调用→提交”p95/p99/最大为 **43.68/61.36/225.75 ms**，“提供→提交”p95 为 **45.93 ms**；重算期相应为 **6.12/134.88/378.72 ms** 与 **112.00 ms**。这同样只验证约 50 条/s 的持久接收，不代表最大接收能力。

## `five-dim` 100 万条失败与修复复测

[失败报告](five-dim-1000000-before-fix.json)和[修复复测报告](five-dim-1000000.json)使用同一生成指纹 `5c42fe20…`：100 万条全热事件、50 条规则、每 20 ms 独立提供消息、容量 4,096 的测试缓冲。此场景同时待执行旧五维、checkpoint、Latency 回放及价格迁移；下表 M1–M6 总时长不能全归因于其中某一项。首次 M6 虽达到 `data_complete`，但丢弃 2,620 条消息触发接收校验错误，后续重算和追赶**未执行**；旧报告中的零值是未测项目。

| 观测 | 首次失败 | 页批次 1,000→100 后完整通过 |
| --- | ---: | ---: |
| M1–M6 费用迁移总时长 | 547.992 s | **772.901 s**，增加 224.909 s |
| 迁移期 inbox 提供／提交／落盘核对 | 27,400／24,780／未运行 | **38,645／38,645／38,645** |
| 缓冲丢弃／峰值积压 | 2,620／4,096 | **0／1,300** |
| 单次写调用最长 | 375.876 ms | **139.115 ms** |
| 提供至提交最长 | 134.339 s | **26.001 s** |
| SQLite trace 单事务写入最长上界 | 354.88 ms | **155.24 ms** |

修复以更长的迁移总时长换得零丢弃；**26.001 s 的最大排队延迟仍表明存在积压**，不能称即时接收或无等待。首次旧五维回放约 130 s、Latency 首次回放约 45 s，连续大量短事务使接收 worker 难获写入机会，并非单个超长 SQLite 写锁。修复后采样的 writer 连接连续 `InUse` 最长为 409.25 s（修复前 176.90 s），这仍是连接占用而不是写锁时长。两次迁移的 WAL 峰值约 35 MiB、含 M1 备份的磁盘峰值约 1.56 GiB；cgroup `memory.peak` 分别约 2.75／2.78 GiB，资源仍为同量级。

修复版重算目标／已处理均为 **333,333**，用时 **188.363 s**，状态 `completed`；重算期另有 **9,419／9,419／9,419** 条消息提供／提交／落盘核对，丢弃和写错误均为 0。两阶段合计 **48,064** 条消息完成一次事件追赶（7.072 s）；迁移后费用 NULL 行为 0，原始 Token 总数在迁移前、迁移后和重算后均为 **2,696,079,191**。重算期真实统计路由返回 `costs_busy` **1,870** 次、意外错误 0 次。修复版二进制哈希及 cgroup 峰值见[环境文件](environment.json)；前后源码哈希分别见[失败](five-dim-1000000-before-fix-source.sha256)与[复测](five-dim-1000000-source.sha256)清单。

## 旧版／新版 119 天 HTTP 对照

旧版产品二进制对应 `54a43cb324f33c1039c7622d842e005257a68466`，新版对应上述 `4e41adc…`。对照脚本对 M1 **旧库备份**和已升级库分别制作 SQLite 副本，顺序启动两个真实 Keeper 进程与本地返回 404 的合成 CPA；每端点先预热一次，再执行 5 次 HTTP 请求。固定查询 `range=custom&unit=day&start=2026-05-26&end=2026-09-21`，覆盖 **119 天**，有意排除锚点前 10 分钟注入消息所在的最后一天，使两库请求及 Token 事实一致。两端 Overview、Analysis 均核得 **991,361 请求、2,672,835,362 Token**；不比较两版费用公式的金额。

| HTTP 路由 | 旧版中位数（5 次） | 新版中位数（5 次） | 本次观察 |
| --- | ---: | ---: | --- |
| Overview | 1,301.07 ms | **71.02 ms** | 中位数约快 18.3 倍 |
| Analysis | 1,706.19 ms | 1,757.33 ms | 中位数约慢 3.0%；5 次样本不足以判断稳定回归 |

原始五次样本和最小／最大值保留在 [HTTP 对照 JSON](query-comparison-1000000.json)。复现时先从上述两个修订构建旧、新产品二进制，再使用首次升级留下的 M1 备份和升级后数据库；脚本会各自克隆到**新**的对照目录，不修改来源文件：

```bash
python3 internal/benchmark/scripts/compare-pricing-queries.py \
  --old-binary <旧版二进制> --new-binary <新版二进制> \
  --backup <M1备份.db> --database <升级后的pricing-old.db> \
  --root <新对照目录> --anchor 2026-09-23T00:00:00Z --samples 5
```

这是一台机器上顺序执行的一组短样本，没有并发用户、CPA 成功响应、重复实验或置信区间；因此仅支持本文所述查询和事实集的观察，不推广为所有查询或整体 ingest 性能结论。

## 源码清单说明与剩余范围

[1m](latest-1000000-source.sha256)与[10m](latest-10000000-source.sha256)启动时源码清单内的 **7 个 runner Go 文件**哈希完全一致，且与当前工作树相同；运行的二进制哈希见[环境文件](environment.json)。1m 清单中的 `run-pricing-benchmark.sh` 哈希不同：1m 直接执行已构建二进制后，脚本才改为可移植的缓存路径与版本传参，所以该差异不改变已记录的 runner 代码或 1m 结果。1m 清单中的对照脚本哈希也早于 HTTP 对照：初稿纳入了注入消息所在日期，随后改为 119 天排除该日；实际执行的对照脚本 SHA-256 为 `f58ad822d8151dd92da06afe732cc04d9dcf28298f07df8bdf043c50649a2130`，与当前文件一致。1m 清单是**启动时**快照，不是后来 HTTP 对照的脚本清单；10m 清单仅含 runner Go 文件。

两次 `latest` 首次升级均未覆盖待执行五维旧迁移的长写入场景；该场景已由独立的修复版 1m 复测覆盖。修复仅把旧五维和 Latency 两个历史回放的页上限从 1,000 改为 100，七个 runner Go 文件未变；`latest` 1m/10m 输入早已应用这些历史迁移，因此其既有实测结果仍适用。修复版二进制 SHA-256 与变更文件哈希见[环境文件](environment.json)和[复测源码清单](five-dim-1000000-source.sha256)。
